## 1. 现状诊断与整改清单

当前工作区代码处于"骨架状态"：`trip_planner_agent.py` 四个节点函数全是 `pass`，`prompts.py` 全部为空，`amap_service.py` 的 `calculate_leg` 是 `pass`，且 `get_route` 调用了**不存在**的 `self.geocode`（直接 AttributeError）。本项目不是修补，而是按新架构重写。

旧方案（git HEAD）被否决，此处仅记录其反模式作为整改对照，**不沿用其任何设计**：

| # | 问题 | 整改方案 |
|---|------|----------|
| 1 | 串行流水线 weather→attraction→hotel→planner，总耗时 = 各 Agent 之和 | 改为 **fan-out/fan-in 并行拓扑**：三个数据 Agent 并行，总耗时 ≈ 最慢的一个 |
| 2 | Agent 间传递大段无结构散文文本，下游靠 LLM 重新"读懂"，信息损耗大 | Agent 间传递**结构化 Pydantic 对象**（WeatherReport / AttractionPool / HotelFoodResult） |
| 3 | 天气只是"调一次接口 + LLM 缩写"，不是真正的 Agent | 天气 Agent 改为 **ReAct 自主智能体**：LLM 自主决定调用 MCP 天气工具的次数、参数、重试与降级 |
| 4 | 预算由 LLM"估算填写"，经常算错 | 预算**完全由 Python 确定性计算**，LLM 只产出单价，不碰加法 |
| 5 | 模块 import 时就实例化 LLM（`fast_llm = get_llm()`），没配 key 时连 import 都崩 | LLM 一律**惰性创建**（函数内获取 + 缓存） |
| 6 | LLM 自由发挥景点/酒店名称，幻觉风险高 | 景点/酒店/餐厅一律**先 MCP 搜真实 POI，LLM 只能从候选池挑选**，禁止编造 |
| 7 | 缺酒店时硬编码 `{city}中心亚朵酒店` 兜底（幻觉数据当真数据返回） | 候选池为空 → 明确降级（hotel=None + errors 记录），绝不伪造 |
| 8 | 同步 `requests` 直接在异步事件循环里跑，阻塞所有并发请求 | 服务层保持同步实现，**异步侧统一 `asyncio.to_thread` 包装** |
| 9 | LLM `request_timeout=30s`，结构化大输出必超时 | 规划总监用 120s 超时实例 |
| 10 | `backend/.env.example` 被删除 | 重建（密钥占位符模板） |

## 2. 总体架构（LangGraph 拓扑）

```
                        ┌──→ weather_agent（气象顾问·ReAct）──┐
START ──fan-out─────────┼──→ hotel_agent（酒店餐厅专家）──────┼──fan-in──→ planner_agent（行程规划总监）──→ END
                        └──→ attraction_agent（景点专家）─────┘
```

LangGraph 实现要点：

- `add_edge(START, "weather_agent")` × 3（三个分支各自从 START 出发，同一 super-step 并行调度）
- `add_edge("weather_agent", "planner_agent")` × 3（planner 有 3 条入边，LangGraph 会等**全部**上游完成后才执行一次——天然 join 屏障，无需手写计数器）
- 三个数据 Agent **互不依赖**（景点 Agent 不再等天气结果；晴雨编排职责全部下沉到规划总监——这正是本设计与旧方案的核心区别）
- 每个节点返回 `dict` 局部状态，各分支写**各自的 key**，无写冲突

### 状态契约（MultiAgentState）

```python
class MultiAgentState(TypedDict):
    request: TripRequest                              # 用户初始需求（只读）
    weather_report: Optional[WeatherReport]           # ← weather_agent 写（已存在于 schemas.py，复用）
    hotel_food: Optional[HotelFoodResult]             # ← hotel_agent 写（新增 schema）
    attraction_pool: Optional[AttractionPool]         # ← attraction_agent 写（新增 schema）
    errors: Annotated[List[str], operator.add]        # 三个分支都可能追加降级信息 → 必须用 operator.add reducer
    final_plan: Optional[TripPlan]                    # ← planner_agent 写
```

**Reducer 规则**：并行分支写同一个 key 时必须有 reducer。只有 `errors` 是多分支共写，用 `Annotated[List[str], operator.add]`；其余 key 一分支一写，默认覆盖语义即可。节点读状态一律用 `state.get(key, default)` 防御。

## 4. 四个 Agent 的详细设计

### 4.1 weather_agent —— 气象顾问（ReAct 自主调用 MCP，本设计的"复杂调用"担当）

**职责**：自主调用高德 MCP 天气工具，产出覆盖出行日期的结构化 `WeatherReport`。

**实现**（这是唯一的 ReAct Agent，体现"复杂调用天气 MCP 工具"）：

1. **工具包装（关键安全措施）**：不要把 MCP 原生 tool 直接塞进 ReAct Agent——`MCPManager.call_tool_text` 里有 `_call_lock` 保护 stdio 持久会话，而 ReAct 内部 `tool.ainvoke` 会绕过该锁，与并行分支的酒店/景点 Agent 产生 stdio 读写竞争。正确做法：

```python
from langchain_core.tools import tool

@tool("maps_weather", description="查询中国城市未来4天天气预报。入参: city(城市名, 字符串)")
async def weather_tool(city: str) -> str:
    """查询指定城市的天气预报（含白天/夜间天气、温度、风力）"""
    return await get_mcp_manager().call_tool_text("maps_weather", {"city": city})
```

把包装后的 `weather_tool` 交给 ReAct Agent，锁语义不变。

2. **ReAct 循环**：`create_react_agent(model, tools=[weather_tool], prompt=...)`（`from langgraph.prebuilt import create_react_agent`，langgraph 1.2.11 支持）。系统提示词要点：
   - 必须调用工具获取真实数据，禁止凭知识回答天气
   - 拿到结果后核对是否覆盖出行日期（高德只预报 4 天）；未覆盖的日期如实标注
   - 一次调用异常可换城市写法（如"杭州市"→"杭州"）重试一次
   - 最终用自然语言汇总逐日天气
3. **结构化收口**：ReAct 循环结束后取最终文本，再调 `llm.with_structured_output(WeatherReport, method="json_mode")` 转成 `WeatherReport`。提示词中必须出现 "JSON"（json_mode 硬性要求）。
4. **降级**：整体 try/except + 单步超时。失败时返回 `WeatherReport()`（daily 为空、coverage.covers_travel_dates=False），并向 errors 追加说明，**绝不向上抛**。
5. LLM 温度 0.2。

### 4.2 hotel_agent —— 酒店与餐厅专家（定向检索 + LLM 甄选）

**职责**：按用户住宿偏好与美食偏好查询真实 POI，产出 `HotelFoodResult`。

流程（非 ReAct，直接工具调用，调用顺序内部串行即可）：

1. **关键词由用户输入驱动**：
   - 酒店：`f"{city} {accommodation}"`（accommodation 如"经济型酒店/舒适型酒店/豪华酒店"），必要时追加"市中心 地铁口"
   - 早餐：`f"{city} 特色早餐 早点"`
   - 正餐：`f"{city} 特色美食 老字号餐厅"`（若 preferences 含"美食"或 free_text 提到具体菜系，追加一轮菜系搜索）
2. 每轮 `call_tool_text("maps_text_search", {...})`，用 `_format_pois_brief`（解析原始 JSON → `- 名称 | 地址 | 类别 | 坐标` 紧凑清单，封顶条数）压缩。
3. **LLM 甄选**：把压缩清单 + 用户需求交给 LLM，`with_structured_output(HotelFoodResult, method="json_mode")` 输出：3~5 家酒店（按价格档拉开梯度）、早餐店 ≥3、正餐厅 ≥4，填 price_per_night / avg_cost / meal_types / specialty / reason。**规则写死在提示词里：只能从给定清单中选，坐标照抄，禁止编造名称**。
4. **降级**：MCP 全失败 → `HotelFoodResult()` 空池 + errors；LLM 失败 → 用解析出的原始 POI 前 N 条构造保底候选（名称地址坐标为真，价格用类型默认值）。

### 4.3 attraction_agent —— 景点专家（多路检索 + 去重 + LLM 参数化）

**职责**：查询目的地真实景点，产出带游玩参数的 `AttractionPool`（8~15 个候选）。

1. **关键词矩阵**：
   - 基础：`f"{city} 热门景点"`、`f"{city} 5A景区 博物馆"`
   - 偏好映射（preferences 每项映射到检索词）：历史文化→"博物馆 古迹"；自然风光→"公园 山 湖"；美食→"美食街 夜市"；亲子→"动物园 科技馆"；购物→"商业街 步行街"；默认补一轮"网红打卡"
   - free_text_input 中若出现明确地名，直接作为一轮关键词
   - 总检索轮数 2~4 轮封顶
2. **解析去重**：从各轮原始 JSON 提取 `name/address/location/typecode/id`，按名称归一化去重（去括号修饰、去"xx风景区(东门)"类重复），合并为候选清单文本。
3. **LLM 参数化**：`with_structured_output(AttractionPool, method="json_mode")`，对候选逐个给出 `visit_duration`（参考：大型博物馆/主题公园 240+、古迹园林 120-180、街区市集 60-120）、`ticket_price`（知名免费景点填 0，不确定填 null）、`indoor`、`reason`。**禁止引入清单外景点**；可按相关性裁剪掉低质候选。
4. **降级**：同 4.2 的兜底策略（原始 POI 直接转候选，visit_duration=120 默认）。

### 4.4 planner_agent —— 行程规划总监（核心编排 + 确定性后处理）

**职责**：融合三份结构化情报，生成最终 `TripPlan`。分两步：**LLM 编排 → Python 确定性后处理**。

#### 第一步：LLM 编排（`with_structured_output(TripPlan, method="json_mode")`，温度 0.4，超时 120s）

提示词硬性规则（这是"合理规划每天行程"的核心算法，必须写进 prompt）：

1. **每日景点个数由游玩耗时决定，而非拍脑袋**：
   - 每日有效游览窗口 ≈ 8 小时（09:00-18:00，含午餐 1 小时）
   - 当日 `Σ visit_duration + (景点数 × 30min 市内移动缓冲) + 60min 午餐 ≤ 480min`
   - 由此推出每天 **2~4 个**：含 ≥240min 大景点（如大型博物馆/主题乐园）时当天最多 2 个；全是 60-90min 小点时最多 4 个
2. **晴雨编排**：读 `weather_report.daily`：`is_rainy=true` 或 `indoor_recommended=true` 的日期优先排 `indoor=true` 的景点；晴天优先户外。无天气数据的日期按常规混合编排。
3. **顺路聚类**：参考候选经纬度，同一天景点尽量同城同片区，减少折返。
4. **餐饮安排**：每天恰好一条 `breakfast` + 一条 `dinner`（从餐厅候选池选，午餐可从简或选小吃 snack），`estimated_cost` 用候选的 avg_cost。
5. **酒店**：全程固定一家（候选池首选），写入每一天的 `day.hotel`，`estimated_cost`=price_per_night。
6. **不要算的账**：`budget` 对象留空或不填——由后处理 Python 精确计算（LLM 只出单价）。
7. `weather_info` 字段由 `weather_report.daily` 逐日映射生成（有数据的日期才输出）。
8. `description`（每日概述）与 `overall_suggestions`（含动线节奏、天气应对、预约提醒）要有具体内容，禁止空话。

LLM 失败兜底：按候选池顺序用 Python 朴素分天（每天 3 个、晴雨不敏感），保证接口永不 500。

#### 第二步：Python 确定性后处理（不用 LLM）

1. **坐标与图片补全（并发）**：对每天每个景点/酒店：
   - `asyncio.to_thread(amap_svc.search_scenic_spot, name, city)` 拿真实坐标/官方实景图/地址（坐标缺失或为 0 时才覆盖）
   - 图片仍缺 → `asyncio.to_thread(unsplash.get_image, name, city)`
   - 坐标仍缺 → `asyncio.to_thread(amap_svc.geocode, city+name, city)`
   - 全部并发 `asyncio.gather`，单点异常静默跳过
2. **每日动线计算（legs）**：路线固定为 `酒店(出发) → 景点1 → 景点2 → … → 酒店(返程)`，逐段 `asyncio.to_thread(amap_svc.calculate_leg, ...)`，交通方式入参取 `request.transportation`（映射：公共交通→transit 口径、打车/自驾→driving 口径、步行→walking 口径、混合→按距离自动）。每段产出 distance_m / duration_min / cost / 中文描述（如"🚇 公交/地铁约 25 分钟 · 6.3 公里（打车约 ¥18）"）。
3. **预算精算（纯 Python，LLM 值一律覆盖）**：
   - `total_attractions = Σ attr.ticket_price`（None 按 0）
   - `total_hotels = hotel.estimated_cost × travel_days`
   - `total_meals = Σ meal.estimated_cost`
   - `total_transportation = Σ leg.cost`（无 cost 时按交通方式日定额：公共交通 30/天，打车/自驾 80/天）
   - `total` = 四项之和

5. **端到端**（需真实 key）：POST `/api/trip/plan`（北京 2 天，公共交通，偏好["历史文化","美食"]）→ 200 且满足：
   - `days` 长度=2，每天 2~4 个景点且每个有 visit_duration
   - 每天 legs 以酒店开头、酒店结尾，段数=景点数+1
   - 每天有 breakfast 与 dinner 各一条
   - `budget.total = 四项之和`（后端打印验算日志）
   - `weather_info` 非空或 errors 中有明确降级说明
6. **前端**：`cd frontend && npx vue-tsc --noEmit` 通过；`npm run build` 通过
